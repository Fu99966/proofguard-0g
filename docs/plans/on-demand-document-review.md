# 按需双模型审查设计稿

状态为待 Owner 确认。此文档描述拟议流程和验收条件。

## 触发条件

每笔交易先走现有的 calldata 解码和确定性规则。通过规则且关联了经验证的链下工单、通告或授权书时，才向两名 0G 审查员提交一次审查。没有文档要求的交易走仅规则路径。应当出具文档的交易由 Owner 配置结构化触发条件，例如新收款人、例外时段或特定动作。缺失、失效或验真失败的材料进入 `REVIEW`，保持 Permit 为空。

两名模型各自只能输出 `BLOCK` 或 `REVIEW`，并附结构化理由及证据位置。任一经验证的 `BLOCK` 会记录否决并终止签发。若无 `BLOCK`，流程进入 `REVIEW`。模型超时、回执无法确认、输出无效或返回集合外的 `ALLOW`，均进入 `REVIEW` 并记录失败原因。

## Owner 人工处理

`REVIEW` 是等待 Owner 复核的明确状态。队列展示交易摘要、规则结果、文档签名状态、证据片段与两个独立裁决。Owner 可以拒绝、要求补件，或通过单独的 EIP-712 签名批准当前版本。批准绑定交易、策略版本、文档清单哈希、审查证据和有效期。签发时重新检查规则、有效期、文档撤销状态和证据绑定。更新交易或文档、策略变化或超时后须重开审查。规则拒绝的交易不能从人工队列绕过。明确 `BLOCK` 由新版本重新提交处理。

## 提交与验真

1. 经过鉴权的 Agent 提交现有交易及本地文档引用。上传器按大小、类型和数量限制接收纯文本、结构化 JSON 与经过隔离提取的 PDF。外部 URL 仅作为引用元数据，服务不代替 Agent 打开或下载任意链接。
2. 本地存储原件和签名清单。清单至少包含原始字节的 SHA-256、发件人和角色、版本、时间窗、适用的 Safe 与网络、允许的交易作用域以及撤销标识。Owner 管理可信签发者和各自允许的文档类型。
3. 使用独立信任根验证签名、有效期和撤销状态。工单系统仅通过预先配置、具备只读权限的连接器核对审批状态及批准者。模型看到的是结构化的验证状态及必要片段。签名有效只说明材料来源和完整性，正文的解释仍交由复核。
4. 对链下事实与交易逐项对照。收款地址、金额、链和时段能结构化时继续由规则核对。签发只引用内容哈希和必要审计字段。原件保存在本地，传给 Router 的字段范围由 Owner 明确授权。

## 防止文档注入

- 在禁网、无密钥的隔离进程中提取文本。忽略脚本、宏、表单动作、外链、嵌入文件和提示词指令。遇到提取失败、加密或歧义版本时转人工。
- 系统指令、已验证元数据和不可信文档片段分字段传入。模型只读，无签发或发起交易的工具，也无法控制外部查询和工作流权限。应用只接受严格的 `BLOCK` / `REVIEW` 输出及原文引用位置。
- 保存原件哈希、提取器版本、实际提供给两名审查员的文本哈希、Router 回执和人工裁决。界面按纯文本渲染文档片段，便于 Owner 对照来源。两次模型响应都不携带执行权限。

## 实施后验收

| 用例 | 预期 |
| --- | --- |
| 无文档要求且规则通过 | 仅规则签发，零模型请求 |
| 文档必需、缺失、签名无效或已撤销 | `REVIEW`，零模型请求，Owner 看到原因 |
| 规则不通过 | `BLOCK`，零模型请求，无 Permit |
| 文档已验真，模型给出 `REVIEW` | 等待 Owner，签发前重新核对规则与证据绑定 |
| 一名模型给出有效 `BLOCK` | 拒绝签发，保存引用位置和回执 |
| 文档夹带指令，或模型返回 `ALLOW`、异常或缺失回执 | 文档指令不获权限。异常输出进入人工队列，无 Permit |
| 人工批准后替换文档、交易或策略 | 原批准失效，重新审查 |

单次审查预计两次模型请求，独立预算待批准。材料正文完整性、来源和模型判断分别留证。目前的评测未证明双模型在规则覆盖之外有增量。
